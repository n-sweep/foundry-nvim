## Notes

### editing ipynbs as different files

The minimal pattern is acwrite + BufReadCmd/BufWriteCmd. Here's the skeleton:

```lua
-- After registering an autocmd for *.ipynb
vim.api.nvim_create_autocmd("BufReadCmd", {
    pattern = "*.ipynb",
    callback = function(ev)
        -- Read the ipynb however you want, put content in buffer
        local lines = vim.fn.readfile(ev.file)  -- raw JSON, or parse & transform
        vim.api.nvim_buf_set_lines(ev.buf, 0, -1, false, lines)
        
        -- Neovim still shows filename as notebook.ipynb
        vim.api.nvim_buf_set_name(ev.buf, ev.file)
        
        -- Intercept saves
        vim.bo[ev.buf].buftype = "acwrite"
    end,
})

vim.api.nvim_create_autocmd("BufWriteCmd", {
    pattern = "*.ipynb",
    callback = function(ev)
        local lines = vim.api.nvim_buf_get_lines(ev.buf, 0, -1, false)
        -- Write the buffer content back however you want
        vim.fn.writefile(lines, ev.file)
        vim.bo[ev.buf].modified = false
    end,
})
```

That's it. Neovim shows notebook.ipynb in the buffer line and title. The buffer content is whatever you put there. On save, you control what gets written to disk. buftype=acwrite is what makes this work — it tells Neovim "I handle saves for this buffer, don't do default file write behavior."

### getting `input()` from neovim

The real fix has two parts: when an input_request comes from the kernel, Python asks Lua for input, then sends input_reply back to the kernel.

Python side — in _retrieve_messages(), replace the stdin logging (lines 177-184) with an actual request/response cycle:

```py
elif msg_type == "input_request":
    prompt = content.get("prompt", "")
    password = content.get("password", False)

    # Ask Lua for user input
    sys.stdout.write(json.dumps({
        "type": "input_request",
        "prompt": prompt,
        "password": password,
    }) + "\n")
    sys.stdout.flush()

    # Wait for response — directly on stdin (main loop is blocked until execution finishes)
    response = json.loads(sys.stdin.readline())
    value = response.get("value", "")

    # Send input_reply to kernel
    self.client.input(value)
```
Lua side — in on_stdout (ipy_bridge.lua line 63-74), detect input_request messages before routing to the result handler:

```lua
local function on_stdout(_, data, _)
    for _, line in ipairs(data) do
        if line ~= '' then
            local ok, result = pcall(vim.fn.json_decode, line)
            if ok then
                if result.type == 'input_request' then
                    local value = vim.fn.input(result.prompt or '')
                    vim.fn.chansend(M.handle, vim.fn.json_encode({
                        type = 'input_response',
                        value = value
                    }) .. '\n')
                else
                    M.on_result(result)
                end
            else
                logger:error('failed to parse: ' .. line)
            end
        end
    end
end
```

The flow ends up:
kernel → input_request (stdin channel)
  → Python writes {"type": "input_request", "prompt": "..."} to stdout
  → Lua's on_stdout picks it up, calls vim.fn.input()
  → Lua writes {"type": "input_response", "value": "answer"} to stdin
  → Python's readline() gets it
  → Python calls client.input("answer") → sends input_reply on kernel stdin channel
  → kernel unblocks input(), execution continues
  → Python finishes IOPub loop, returns execution result to Lua
